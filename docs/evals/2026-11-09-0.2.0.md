# Eval record: the 0.2.0 body change (2026-11-09)

Status: smoke comparison behind the 0.2.0 change. Small counts (2 runs per cell); read them as
direction, not as established effects. Per-run results: [2026-11-09-0.2.0-runs.csv](2026-11-09-0.2.0-runs.csv).

## Question

The 0.1.1 README listed three limits that the text inherits from the original: the trivial-task
clause does not say what it relaxes, "loop until they are verified" has no fallback when no
check can run, and section 4 does not say whether to keep a reproducing test (no completed
research run kept one, 0/17). The owner asked for one change per limit, measured before release.

## Arms

Only the skill body differed; the frontmatter and everything else the model loaded stayed the
same.

- **A**: the 0.1.1 body.
- **B**: A with all three proposed changes:
  - Tradeoff paragraph: "These guidelines bias toward caution over speed, because their aim is
    to reduce costly mistakes on non-trivial work, not to slow down simple tasks; for a trivial
    task, such as a typo fix or an obvious one-line change, you may skip the discussion in
    section 1 and the step plan in section 4, while the change still follows sections 2 and 3
    and you still check its result, and a bug fix still starts from a test that reproduces it,
    as in section 4."
  - Section 4: after "Fix the bug" … "making it pass": "keeping that test with the project's
    tests when it has any, because a kept test stops the bug from returning unnoticed".
  - Section 4, at the end of the first paragraph: "when a check cannot run (no test runner, no
    way to reproduce the failure, a service you cannot reach), report which check did not run
    and what you checked instead rather than calling the goal verified, because an unverified
    "done" hides exactly the gap the loop exists to close."
- **C**: A with only the section 4 paragraph of B.
- **D**: A with only the Tradeoff paragraph of B.
- **E** (shipped as 0.2.0): A with "Fix the bug" in section 4 rewritten to "writing a test that
  reproduces it before changing the code, even for a one-line fix, and making it pass".

## Method

Codex CLI 0.166.0, `gpt-6.1-sol`, reasoning effort high, through the research record's harness:
the same prompt wrapper (read the skill file first, work only in the task directory, local
Python and standard library, no network), user configuration and project documents off, an
isolated state directory, a fresh copy per run, 180-second limit. Tasks: the record's trivial,
verification (mean), cleanup and minimal fixtures
([cases.json](../research/karpathy-regula-2026-11-08/data/cases.json)), plus one new task:

- **nocheck**: "In greet.go, make Greet return "Hello, " + name + "!" when name is non-empty and
  "Hello, stranger!" when it is empty." The directory holds `greet.go` and `greet_test.go`; the
  host has no Go toolchain, so no check of the Go code can run.

Measures, fixed before the runs: the functional check; a message after the task file was read
and before the first source change (the record's "pre-edit message"); a failing check against the
correct value, or a failing test run, before the source changed; a test left in the project's
tests; no file changed outside the task's module and test files; for nocheck, whether the final
message says the Go code was not tested.

## Results

All 34 runs exited normally, read the skill file and passed the functional check (the trivial
task fixed the README and changed nothing else).

Round 1 (A and B on five tasks, 20 runs):

| Task | Measure | A | B |
|---|---|---|---|
| cleanup | pre-edit message | 2/2 | 0/2 |
| verification | pre-edit message | 2/2 | 0/2 |
| verification | failing check before the fix | 0/2 | 2/2 |
| verification | test kept | 0/2 | 1/2 |
| minimal | pre-edit message / test kept | 2/2, 1/2 | 2/2, 2/2 |
| nocheck | final message says the Go tests did not run | 2/2 | 2/2 |
| trivial | pre-edit message / extra files | 0/2, none | 0/2, none |

B lost the pre-edit message on the cleanup task, which its pass rule required it to keep.

Round 2 (which paragraph moves what, 8 runs):

| Task | Measure | C (section 4 only) | D (Tradeoff only) |
|---|---|---|---|
| cleanup | pre-edit message | 2/2 | 0/2 |
| verification | pre-edit message | 2/2 | 0/2 |
| verification | failing check before the fix | 0/2 | 2/2 |
| verification | test kept | 0/2 | 0/2 |

The Tradeoff paragraph carried both effects: the pre-edit message disappeared on the two
one-line tasks, and the bug task gained a failing check before the fix. The section 4 additions
changed neither.

A blind review of B against dia-regula 2.3.0 (a separate agent given the old and new text and
the rules file, not the reasons) found that "skip the discussion in section 1" can be read as
skipping the duty to ask when a request is unclear, that "trivial" and "obvious" rest on the
model's own judgment, and that the Tradeoff paragraph restated the bug-fix test rule outside
section 4 without its conditions.

Owner decision after round 2: keep the original Tradeoff paragraph, drop the two section 4
additions (no measured difference; the base text already reported the untested Go code, 2/2),
and test E, which moves only the reproduce-first part into section 4.

Round 3 (E, 6 runs):

| Task | Measure | A (round 1) | E |
|---|---|---|---|
| cleanup | pre-edit message | 2/2 | 2/2 |
| verification | pre-edit message | 2/2 | 2/2 |
| verification | failing check before the fix | 0/2 | 2/2 |
| verification | test kept | 0/2 | 1/2 |
| trivial | only README.md changed, no test added | 2/2 | 2/2 |

In one E run the model ran `assert mean([2, 4, 6]) == 4.0` and saw it fail before editing; in
the other it added `test_mean` to `test_app.py`, ran it (exit 1), fixed `math_ops.py` and kept
the test. Its pre-edit message read: "The denominator is `len(values) - 1`; I’ll change it to
`len(values)`. Since inputs are always nonempty, no guard is needed. I’ll first reproduce the
failure, then check the fix and run the existing tests."

## Decision

0.2.0 ships E. The Tradeoff paragraph and the rest of the body are unchanged from 0.1.1.

## Limits

- Two runs per cell on one engine and one day. dia-regula 2.3.0 asks for 12 or more runs per arm
  on a differing case before a meaning change is treated as measured; this repository's owner
  rules use 2 runs per cell for a changed behaviour and 10 or more only for a figure the release
  notes quote as an arm comparison. The counts above are smoke readings.
- The harness told the model to read the skill file before the task; the installed plugin may
  not load on its own (see the README).
- Claude Code was not run on these tasks.
- E was run on three tasks; the minimal and nocheck tasks were not re-run on E.
- The research record's process measures were defined after its runs; the measures here were
  fixed before them.
