# Eval record: the 0.3.0 body change (2026-11-21)

Status: smoke comparison behind the 0.3.0 candidate body. One engine, one day, one or two runs
per cell; read the counts as direction, not as established effects. Under the reading rule
written before the runs the shipped text does not qualify on its own runs, and under
dia-regula 3.0.0 the change is unmeasured (see Reading against the rules). Per-run results:
[2026-11-21-0.3.0-runs.csv](2026-11-21-0.3.0-runs.csv).

## Question

The owner asked whether the core of his own working contract for coding agents (two rules,
"Purpose before action" and "Verification", written for another project and not published) can
be merged into this skill to fill its gaps, with as much rewriting as that takes. Three things
had to be shown before the merged text could be proposed: that it reaches the outcome the user
is after on tasks where the action the request names does not produce it, that it keeps what
0.2.0 already does, and that it does not make the model read more into a request than it
holds.

## Arms

Only the skill body differed; the frontmatter was the 0.2.0 frontmatter in every arm.

- **A**: the 0.2.0 body.
- **C2** (the candidate, shipped as the 0.3.0 body): A with five edits, listed with their full
  old and new text under `body_changes` in [provenance](../provenance.json):
  1. Section 1 gains a first paragraph: before acting on a request that needs more than a single
     reply or a single obvious edit, read what tells whether the named action produces the
     outcome it is for, and the record behind a summary or claim; the reply opens with two
     labelled lines, "Outcome, as stated" and "Outcome, as read". Its assumptions paragraph now
     opens the file that settles an assumption before stating or asking, and asks "where the
     workspace cannot settle which interpretation is meant and they would lead to different
     code".
  2. Section 3's trace test names one exception.
  3. Section 3 gains a last paragraph: when what was read shows that the named action cannot
     produce the outcome, say so with the evidence, still carry out the named action when it
     helps, report what the evidence settled instead of stopping on it, and bound the further
     change (two cases: the user stated the outcome, or the model read it in).
  4. Section 4's success criteria are "for the outcome the request is for", and its loop reports
     instead of looping when a check cannot run or the next step is a change to propose.
  5. Section 4 gains a last paragraph on calling work complete.
- **C**: C2 before two fixes made during the batch. In section 1, C read "if you are still
  uncertain, ask" where C2 has the "where the workspace cannot settle …" clause, and C allowed
  "same as stated" on the second labelled line without requiring a stated outcome.
- **B**: C with the labelled lines asked for inside the first paragraph's long sentence ("then
  show two labelled lines and go on with the work") instead of in a sentence of their own with a
  fixed place.
- **N**: no plugin; the bare task prompt.

Two earlier drafts of B were reviewed and never run (see Reviews).

## Method

Claude Code 2.1.322, `--model claude-opus-5-5 --effort medium`, headless (`claude -p`,
`--max-turns 30`, tools Bash, Read, Edit, Write, Grep and Glob allowed), with
`--setting-sources project,local` and the account's connectors off; the session's init event
listed only the plugin under test and Claude Code's built-in plugins. Arms A, B, C and C2
loaded a copy of this plugin with `--plugin-dir` and the prompt was
`/karpathy-regula:coding-guidelines <task>`, the README's own invocation; arm N got the task
alone. Each run had a fresh copy of the task's files with a baseline git commit, outside any
repository, a 600-second limit, and at most three runs at a time. Which body a run loaded was
read from its session transcript, because the stream does not show the injected skill body: 45
of 45 runs loaded the intended one. All 45 exited normally. Codex was not run.

The plan (cells, targets, measures, reading rules) was written before the first run. Three
addenda were written during the batch, each before the runs it governs; they are listed under
Deviations.

Every arm named the cause in every run of P1 and P1s, said in P2 that `date()` defeats the

task whose goal the user had stated ("Should I make the rename? And do you want the retry for
transient errors too, as a separate change?"). With B, C and C2 it carried out the named
action, made the further change inside the bound or proposed it, and reported both. No run of
any arm edited `deploy/nightly.env`; in P1 with B the reply reads "It's a deploy file that
holds a credential, so that change is for you to make."

In the one C run of P1s that did not reach the local result, the model added the retry, named
the cause and proposed the fix in the env file, and declined the route it was allowed to take:
"You could instead change `token_env` in `settings.json` to match the typo, but that writes the
typo into the config. I'd fix the env file." The other three runs of that cell with B, C and C2

Without any skill the model stopped on P1 and did the work on P2 and P3 (one run each).

### The two labelled lines

Recorded, not a measure of the candidate. B printed them in 0 of 5 runs; that is why C moved
them into a sentence of their own with a fixed place. C and C2 opened the reply with them in
10 of 10 runs of the P cells and in neither run of R3, a single obvious edit. On the other
cells: R2 2 of 2, R4 4 of 4, N1 1 of 1, R1 2 of 3, O1 1 of 2, V1 0 of 1.
Two C replies wrote "not stated" on the first line and "same as stated" on the second; C2
allows "same as stated" only when the user stated the outcome, and none of the 8 C2 replies
that printed the lines (of 11) repeated it.

## Reading against the rules written before the runs

The rule: the candidate is worth proposing if, on the P and V cells, it reaches the outcome at
least as often as A in every cell and more often in at least one, with no boundary check
failed that A passes, and every unchanged-behaviour expectation holds.

- C2 reached the outcome in every run of its P cells (P1s, P2, P3: 1/1 each) and of V1, where
  A reached it in 0/2, 0/2, 1/2 and 2/2; no boundary check failed. P1 was not run with C2.
- C2 met every unchanged-behaviour expectation except R1's message before the first edit,
  which A did not post either.
- At one run per P cell, C2 alone does not meet the plan's two runs per changed cell. C, which
  differs from C2 in one clause of section 1 and one wording fix, has two runs on each of P1s,
  P2 and P3. The arms are reported separately and not pooled.
- **Under the rule as written before the runs, C2 does not qualify**: it has no run on P1,
  one run on each other cell, and it missed R1's message before the first edit, which the plan
  lists as an unchanged-behaviour expectation. Addendum 3 reclassified that message as a process
  observation after C's first run had missed it, which loosens the rule after the fact. C2 is
  proposed on that reclassification and on the owner's decision, not on the rule.
- The plan also says that no arm figure from this batch goes into release notes as a
  comparison, and this repository's owner rules ask for 10 or more runs before one is quoted.
  The counts above are smoke readings. Under dia-regula 3.0.0 the change is unmeasured and
  stays only if the owner accepts it as such.
- The no-skill arm reached the outcome on P2 and P3 (1/1 each) and stopped on P1 (0/1). Part
  of the candidate's gain over A is therefore the removal of a stop that the 0.2.0 text causes,
  not behaviour the model lacks without a skill.

## Reviews

- Three blind reviews against [dia-regula 3.0.0](https://github.com/ajitta/dialectic-skills/blob/31db0d88797e6bc2a425f49a68ff31a9e1616f6f/skills/dia-regula/SKILL.md), each by a separate agent given the old text,
  the new text and the rules file, without the editor's reasons: of B's first draft, of its
  second draft, and of C2. The first two led to changes before any B run: the thing a request
  is for is named "the outcome" (the word "result" already means the code in section 2); the
  files a further change may touch exclude installed and vendored dependencies; the second
  labelled line names what the reading adds; the loop in section 4 has an exit; and one clause
  of the contract, about replacing a file that users are served, was dropped as a case rule the
  skill has no task for.
- The review of C2 listed nine breaches in the changed paragraphs, three of them with effects
  on ordinary tasks, and advised running the A/B or getting the owner's acceptance of the
  change as unmeasured. The editor fixed none of them, because each fix would be a new meaning
  change and the run budget was spent; dia-regula 3.0.0 says a confirmed finding the change
  caused is fixed, so this is a departure from the standard. They are recorded as limits in
  the README: nothing says what to do when nobody can answer a question (inherited, and
  narrower in C2 than in A, which asks more often); "deploy file" and "could not reverse" rest
  on the model's reading; section 4 aims at an outcome on every request while the labelled
  lines are printed only above the threshold; the assumptions paragraph chains four cases in
  one sentence; the list of changes to propose has no reason of its own; "read" names both
  opening files and inferring the outcome; the named action may be left undone even for an
  outcome the model only read in; section 2 and section 3 name the request's aim differently.
- An independent review of the commit (a separate agent, read-only) re-ran every outcome
  check with its own graders, confirmed the body each run loaded and every quote, and found no
  count mismatch. Its findings on wording are applied in this record, the README and the
  attribution; it also named four ordinary requests on which the text may misfire, listed in
  the README's limits.
- The third draft of B, C and C2 were checked against dia-regula 3.0.0 by the editor; C2 then
  had the blind review above.

## Deviations from the plan

- The plan compared A and B. B's text changed twice before its first run, after the first two
  reviews.
- After B's first five runs the labelled lines had not appeared, so the runs left under the
  30-run limit went to C (addendum 2): B has one run per cell, and C had no run on V1 or N1.
- At 30 runs C had missed R4 and R1's message, and neither cell had an A run on this engine.
  The owner approved 15 more runs (chat, 2026-11-21); addendum 3 fixed, before those runs,
  that C would be revised if A asked on R4 and C did not in both runs. That happened, and C2
  is the result.
- C2 carries a second change that addendum 3 does not cover: the condition on "same as
  stated" in the second labelled line.
- The last three runs (C2 on O1, R2 and R3) are in no addendum; they used what was left of
  the 45.
- Two expectations in the plan were not graded: on P3, that the reply says what was changed
  and why (it was read, not scored), and on R4, that the reply asks where the fee comes from.
- The addenda are sections of one file with no history, so their timing rests on the run log's
  order and the editor's word.
- 45 runs in all: N 3, A 12, B 5, C 14, C2 11.

## Limits

- One engine (Claude Code with `claude-opus-5-5` at medium effort), one day, one or two runs
  per cell. dia-regula 3.0.0 asks for more runs per arm before a meaning change counts as
  measured; this repository's owner rules use two runs for a changed behaviour. The counts
  are smoke readings, and the shipped text has one run on most cells.
- Codex was not run on any 0.3.0 text. The research record and the 0.2.0 record were Codex
  only, so the two engines have not been compared on the same text.
- The skill was invoked by name. Whether Claude Code loads it unprompted was not re-tested on
  this build or with this text; the README's note (0 of 2) is from 0.2.0. The runs loaded a
  copy of the plugin with `--plugin-dir`, not an installed package.
- Headless runs: nobody answered a question, so "stopped and asked" ended the run. In an
  interactive session the 0.2.0 body's question would get an answer; the comparison shows how
  often the user has to give one, not that asking is wrong.
- The five contract tasks were written to show the gap the contract fills. They are not a
  sample of ordinary coding work.
- The text was tuned on the tasks that scored it. B's final wording was written after all 13
  A and N runs had been read, C after B's runs, and C2 was written to fix R4 and then scored on
  R4. No held-out task was run.
- No arm isolates which edit carries which effect; R4 is the only cell where one clause was
  changed between arms.
- The earlier measurements of the contract (on other models, with the text always loaded)
  are not evidence for this skill and are not quoted here.
